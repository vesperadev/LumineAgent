# AGENT.md — 十评审团队章程

本目录是「十评审」的执行说明书。根级 `../../AGENTS.md` 是多 AI 协作的硬约定，本文件**不覆盖**它，只把它第 8 条（"代码交付前必须经另一个 AI 审查"）扩成可执行的十人分工。

原则用法与根级一致：**先看这一条能不能被验证**。说不清怎么验的规则就是口号，落地时会被绕过。

---

## 1. 谁评、评什么

十个评审员，一人一个维度，**互不重叠**。分工按"一个人能同时盯住的几件事"划，不让两个人评同一件事。

| 评审员 | 管什么 | 不管什么 |
| --- | --- | --- |
| R1 正确性 | 逻辑对不对、边界与空值、状态机 | 接口要不要改 |
| R2 契约与影响 | 接口/类型/事件契约有没有被悄悄改 | 内部结构 |
| R3 架构与边界 | 分层、依赖方向、重复入口 | 单行写法偏好 |
| R4 测试与证据 | 改动有没有被用例触达、不可测部分有没有点名 | 项目方向 |
| R5 安全与稳健 | 密钥、路径、注入、坏输入会不会打穿 | 性能 |
| R6 并发与异步 | 流/取消/监听器/竞态的时序 | 命名 |
| R7 性能与分配 | 热路径浪不浪费、包体与重渲染 | 正确性 |
| R8 命名与注释 | 名字是否说谎、注释是否与实现一致 | 功能取舍 |
| R9 兼容与文档 | 旧行为、README/roadmap 是否对账 | 新功能设计 |
| R10 可观测与错误信息 | 出错时人能不能据此动手、日志有没有泄漏或丢上下文 | 错误分类之外的架构 |

每个评审员的完整人设在同级 `R1/AGENT.md` … `R10/AGENT.md`。

## 2. 只评本次改动，不评全局

- 评审对象是**本轮 diff**（或点名指定的文件集合）。评审员看不到未改动文件，说"信息不足"不算缺陷，不许照着它去改。
- 结论只能落在能指着 `文件:行` 的地方。提不出位置的，写"建议"也要给出依据。
- 不讨论项目方向、不要求换技术栈、不要求重构模块边界。真觉得结构不对，标 `[建议]` 并写"建议"二字。

## 3. 严重度只有三档

- `[阻断]`（P0）：会造成**错误结果、丢数据、崩溃、静默失败**。这一档非零就不许提交。
- `[应改]`（P1）：提交前该改，但改错也不至于出错结果。**必须逐条处置**（修，或不修并写明理由）。
- `[建议]`（P2）：口味与优化。只进记录，不阻塞。缩进、命名偏好、日志文案、阈值高低、注释时态一律放这一档。

**把口味标成 `[应改]` 是评审自身的缺陷**。一条意见拿不准，就降档，并在正文写清"我不确定这是不是缺陷"。

## 4. 评审员没有编译器

- 派发方必须先跑门槛，把真实结果注入人设，例如：`cargo test 2 passed / 0 failed`、`cargo clippy --all-targets -- -D warnings` 零警告、`npm run build` 47 modules 零错误。
- 评审员不跑命令、不改文件、不 `git commit/push/branch`、不联网、不调用真实模型。
- 看到"我这里编译不过"要先怀疑自己：除非 diff 里能看到明确的类型错误，否则不许把"应该编译不过"写成结论。

## 5. 派发口径

一次派发必须给齐四样，缺一样评审员就有权只回"信息不足"：

1. 评审员编号与人设路径（`Docs/agents/R<n>/AGENT.md`）
2. 本轮 diff 或文件清单（用 `git diff --stat` 与逐文件 diff，或直接给绝对路径）
3. 门槛实跑数字（见 §4）
4. 需要重点核对的三件事（契约一致性 / 安全 / 边界，按改动类型挑）

## 6. 收回来的处置（没有第三类）

每条意见只能落成"修"或"不修"：

- **修**：当场改，改完重跑门槛，全绿。同一轮意见全处理完，再发下一轮评审，不边改边发。
- **不修**：必须写下依据——是核对过代码事实的假结论，还是超出本格范围（记 TODO，不顺手改），还是要留到下一格的取舍。理由写进回复与提交正文，别只在脑子里。
- 单票与多票一视同仁：多票同一点优先修；单票先核对事实，真就修，假就记理由。**不因为只有一票就放过真问题**。

## 7. 收敛判据（三条同时成立）

1. 门槛全绿，且测试条数不低于基线；
2. `[阻断]` 为 0；
3. 剩下的每条 `[应改]`/`[建议]` 都有书面处置理由。

满足即可提交。**不为了归零去改口味、改措辞、删断言、放宽判定口径**——这比留一条"应改"更糟。

## 8. 轮次纪律

- 同一批评审员从一个改动跟到收敛，中间不换人；每轮十份全部重跑，不许挑"上一轮没提意见的那几个"省调用。
- 每人只带自己的历史：请求里只注入**该评审员本人**上一轮的结论，看不到别人的。
- 带历史只有两个用途：不重复、不改口。已修的点禁止再提；要改口必须明写"上一轮我错了：因为…"。
- 每格至少两轮：第一轮全部"通过"也要再跑一轮确认收敛，不能一轮定稿。
- 连续三轮仍冒出新的阻断/应改：停手，判定这一格方向或粒度错了（拆小、回退、先补结构），不许靠改注释把评审改绿。

## 9. 互斥意见

同一处代码被要求改成两个互斥写法（例如"加防御分支"与"删掉这个防御分支"），处置口径：

- 取一条实现，另一条在提交正文写"同一处存在互斥意见，取了 X，理由是 Y，故不做 Z"；
- 同一处连续两轮出现互斥意见，判定为评审噪声，不再为这一处改代码，只留书面记录。

真缺陷（阻断级、能复现的错误）没有"互斥"豁免。

## 10. 留档

每轮写进当日记录或提交正文：第几轮 / 十份结论分布（各几阻断几应改几建议）/ 修了几条（都是什么）/ 不修几条（都为什么）/ 当轮门槛数字。评审全文留在终端或临时目录即可，不必入库。

## 11. 本项目专属的几条红线

- 只用无效占位 key（如 `sk-invalid-for-error-path-test`）证明错误路径，**不用真实 key 发正式请求**；每轮真实上游调用不超过 1 次，能离线测的一律离线。
- `src/styles/globals.css`、`typography.css`、`ui/icons/` 与 Percho 上游逐字一致，**评审不许建议改它们**；换皮只允许动 `--color-*` token。
- 工作区可能有别人未提交的改动，评审员不许把它们算进 diff，也不许建议"顺便一起改了"。
- 任何结论都不得回显密钥原文，连片段也不行。
